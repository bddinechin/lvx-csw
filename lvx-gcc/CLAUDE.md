# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this directory is

`lvx-gcc/` holds the GCC side of the LVX toolchain, shaped like `lvx-llvm/`: a plain
directory in `lvx-csw` containing a submodule that is a genuine GitHub fork of upstream.

- `lvx-gcc/gcc` → `bddinechin/gcc`, a fork of `gcc-mirror/gcc`, branch **`lvx-gcc`**.
- Base is **trunk (`BASE-VER` 17.0.0, experimental)**, not a release branch. A backport to
  a numbered release was considered and deliberately not done.
- The backend therefore lives at `lvx-gcc/gcc/gcc/config/lvx/` — one level deeper than the
  path suggests, exactly as `lvx-mlir/llvm-project/mlir/...` is. Paths below that start
  with `gcc/` or `libgcc/` are relative to `lvx-gcc/gcc/`.

This file is deliberately **outside** the fork so the fork carries no non-upstream files.

## Ground truth for the ISA

`lvx-binutils/opcodes/lvx-opc.c` is the authority for what instructions exist. It is
generated by `lvx-mds`'s `BE/GBU` from the machine description, so it *is* the ISA. Every
entry carries its core:

```
/* Opcode-lvx_v1-MULXWD_... */   .as_op = "mulxwd",
/* Opcode-lvx_v2-MULWQ_...  */   .as_op = "mulwq",
```

lvx_v1 has 410 mnemonics, lvx_v2 has 703; **293 are lvx_v2-only and none is lvx_v1-only**,
so lvx-2 is a strict superset and `LVX_2` alone is a sufficient gate.

### Auditing the machine description against it

A `.md` naming an instruction that does not exist is **not a build error**. It fails only
when the pattern is finally selected and the assembler rejects the output, so bad mnemonics
accumulate silently — 136 of 304 literal ones had, before the first audit.

```bash
make -C /home/bd3/lvx-csw/lvx-gcc-build/gcc mddump
# -> lvx-gcc-build/gcc/tmp-mddump.md
```

`tmp-mddump.md` expands **every pattern per iterator**, so the output templates are
concrete. Extract the leading token of each and check it against the `.as_op` set. Grepping
the `.md` sources instead misses everything behind an iterator: `"mul<widenx> %0 = %1, %2"`
is invisible to a literal grep but expands to real mnemonics that may not exist. The dump
also carries a `;; <file>: <line>` comment per construct, so a finding maps back to source.

Names built from an attribute (`<stem>bx`) cannot be checked directly — expand the attr
over the pattern's own iterator and require the result for *every* value, since one
define_insn covers them all.

## Architecture gating

SIMD is **lvx-2 only**. Every packed arithmetic instruction — `addho`, `addwq`, `adddp`,
`compdp`, `negho` — is `Opcode-lvx_v2`. `-march=` accepts `lvx-1` (default) and `lvx-2`;
`lvx-opts.h` defines `LVX_1`/`LVX_2` and patterns emitting a v2-only mnemonic carry
`LVX_2` in their condition.

Gating patterns is not enough on its own: `TARGET_VECTOR_MODE_SUPPORTED_P`
(`lvx_vector_mode_supported_p`) must return false for lvx-1 too, or the middle end forms
vector values it has no pattern to operate on and an explicit `vector_size` type ICEs with
"unrecognizable insn" instead of being lowered element-wise. Ordinary scalar C never hits
this, so the differential harness will not catch it.

The `HAVE_LVX_*` macros in `lvx-opts.h` are compile-time capability switches inherited from
KVX, many frozen at `(0)`. Several gate a path whose alternative is the *live* one, so the
`(0)` branch is what actually runs — check the value before assuming a guarded pattern is
dead, and check whether the instruction now exists before leaving one at zero.

## Instruction width: one instruction, not a pair

The port originally issued 128-bit SIMD as **two 64-bit instructions on the `%x`/`%y`
register halves**, and 256-bit as four:

```
add<chunkx> %x0 = %x1, %x2\n\tadd<chunkx> %y0 = %y1, %y2      ← addhq: exists on neither core
```

`<chunkx>` is a mode's 64-bit chunk suffix, `<suffix>` its own, `<hsuffix>` the suffix of
its 128-bit half. The collapsed forms are `add<suffix> %0 = %1, %2` at 128-bit and, at
256-bit, two instructions addressed with **`%L`/`%M`** — the least- and most-significant
128-bit half of a 256-bit operand (`lvx_pgr_reg_name (REGNO)` and `REGNO + 2`).

`%L`/`%M` are **uppercase because they must be**: `output_asm_insn` in `final.cc` intercepts
`%l` (label), `%a` (address), `%c` and `%n` before they reach a target's `print_operand`, so
a lowercase `l` case is unreachable and ICEs with "'%l' operand isn't a label".

Bitwise ops are the exception that needs no gate: `iorq`, `andq`, `eorq`, `nandq`, `niorq`,
`neorq`, `andnq`, `iornq`, `copyq`, `notq` are on **lvx_v1**, and with no carry between
lanes the `q` form is exactly two independent `d` ops. This does **not** extend to
arithmetic — `addq` is a single 128-bit add *with* carry across the halves, not two 64-bit
adds, so `addd` pairs must become `adddp` (v2-only), never `addq`.

## Hardware primitives that replaced software sequences

- **divide/modulo** — `divmodw`, `divmoduw`, `divmodd`, `divmodud`, all lvx_v1, one
  FULL-slot instruction writing quotient into the low 64 bits of a 128-bit pair and
  remainder into the high 64. Signed and unsigned **must use distinct unspecs**
  (`UNSPEC_DIVMOD` / `UNSPEC_DIVMODU`): with one shared unspec the patterns have identical
  RTL, recog matches whichever comes first, and unsigned division silently emits the signed
  instruction. Nothing static catches that — it builds, the mnemonics exist, mddump agrees.
  The 32-bit forms use `.sx` so the SImode result is sign-extended as sub-word values are
  held in registers; the zero-extending form exists so a SIMD divmod can be composed by
  OR-ing shifted lane results without masking. Division by zero returns zero rather than
  trapping, so `-mdivmod0-trap` still needs the explicit check (`lvx_expand_divmod`).
- **square root** — `fsqrth`/`fsqrtw`/`fsqrtd`, all lvx_v1, exact and one instruction. At
  default settings each is paired with a libm tail call, which is correct rather than a
  shortfall: `-fmath-errno` is on, so a negative argument must set `errno`. Under
  `-fno-math-errno` no libm reference remains.
- **lane extension** — `WIDEN*` (`widensbho`, `widenshwq`, `widenswdp` and the `z`/`q`
  variants) reads a 128-bit vector and selects its least or most significant half via the
  `mostsig` modifier. `EXTL*` is the other lane-extension family but selects **even/odd**
  lanes, so it does not express a sequential widening. `FWIDEN*` is the FP counterpart.

## MDS-generated files — do not hand-edit

`gcc/config/lvx/lvx-registers.h` and `lvx-registers.md` are `BE/GCC` output and are
byte-identical to `lvx-mds/lvx-refs/BE/GCC/lvx/`. They had previously drifted into
hand-maintained files — an `EGR_REGS` class added by hand, a stale `rvc` register name, a
different `LVX_FRAME_POINTER_VIRT_REGNO` — which is the failure mode to avoid.
`lvx-mds/lvx-family/BE/GCC` does not exist yet, only the family-agnostic `MDS/BE/GCC`.
`lvx_builtins.h` and `lvx_macros.h` remain hand-written.

There is **no register-parity constraint**. LITE instructions used to need their W and Z
operands to share a parity, satisfied by an `EGR_REGS` class and an `"R"` constraint letter;
the ISA refactoring removed every Format relying on those classes, so `EGR_REGS`,
`OGR_REGS` and the `"R"`/`"Q"` constraints are gone and those operands take plain `"r"`.

## Immediate operands: read every opcode entry

A mnemonic has **several entries** in `lvx-opc.c`, one per encoding width, exactly as
`maked` has simple/double/triple forms. Grepping the first entry and stopping will make a
register-only instruction of one that takes an immediate in its double-word form.

The rule worth knowing: **any Format whose name ends `.W` or `.M` enables a sign-extended
32-bit immediate**, in the *third* operand slot. So

```
ADDSD    formats: [ ALU_DWRR1, ALU_DWRR1.M ]                        -> imm32 only
ADDD     formats: [ ALU_DWRR0, ALU_DWRR0.M, ALU_DWRI, .X, .Y ]      -> imm32 + s10/s37/s64
```

Both take an immediate; only `addd` also has the short `ALU_DWRI` forms. An instruction
with no `ALU_DWRI` variant must not offer `I10`/`I37`/`i` constraints.

Because the immediate is in the third slot, **which GCC operand may carry it depends on
the template's print order**:

```
addusd %0 = %1, %2    -> operand 2 prints last, so operand 2 takes the immediate
sbfusd %0 = %2, %1    -> operand 1 prints last, so operand 1 takes it
```

Getting that backwards yields `sbfusd $r1 = 4, $r1`, which the assembler rejects with
"expected one of [RegClass_lvx_v1_singleReg]" — an *operand-position* error the mnemonic
audit cannot see, since the mnemonic itself is real. Only assembling finds it.

And note `gen_*` functions do not check predicates: an expander calling
`emit_insn (gen_foo_2 (...))` directly can hand a constant to a register-only slot, which
becomes unmatched RTL and an ICE rather than an assembler error. Use `force_reg` there.

## Keep GCC proper untouched

The only files shared with other targets that this port modifies are the three registration
hooks every port has: `config.sub`, `gcc/config.gcc`, `libgcc/config.host`. `gcc/rtl.h` and
`gcc/common.opt` were reverted to upstream — a `MEM_NON_TEMPORAL_P` that nothing ever set,
and a `-fmodulo-sched-bundle` only `lvx.cc` read (now a `Target` option in `lvx.opt`).

Resist adding to that list. If something seems to need a change in GCC proper, check first
whether anything actually consumes it.

## Validating a change

The oracle is `lvx-gem5/tests/lvx/diff/run_diff.sh`: compile the same C with the host `cc`
and with `lvx-mbr-gcc`, run the LVX binary under the gem5 ISS, compare exit codes. Baseline
is **10/10**. It is deliberately scalar and libgcc-free, so it will not exercise SIMD,
vector types, or division helpers — test those separately, and test signed and unsigned
variants *apart* or a mismatch will not say which half is wrong.

For build and reconfigure recipes use the `build-lvx-toolchain` skill.

## Known broken

- **libgcc does not complete.** `unwind-sjlj.o` and `unwind-dw2-fde.o` ICE in the `mach`
  pass (`pass_lvx_shaker`) — the same pass as a known `-O0` ICE, and `t-lvx` already carries
  a `-fno-hwloop` workaround for those two files. Reproduces only with the full build
  command, including `-fvisibility=hidden -DHIDE_EXPORTS`.
- **73 mnemonics reachable on lvx-1 do not exist**, 43 of them XVR. The rest need per-value
  work: their iterator mixes values that have a 128-bit form with ones that do not
  (`rol`/`ror`/`clz` are scalar-only), or they are families with no LVX instruction at any
  width (`fsdiv`, `fcdiv`, `ffdma`, `fmm`).
- `libgcc/config/lvx/divmodvx{si,hi,qi}.c` are left out of the default build: they are
  written against vector types and SIMD builtins, and reference builtins removed with the
  KVX cleanup. They need updating alongside an lvx-2 multilib.
- **`__divv4sf3` and the other vector FP dividers are undefined.** The scalar `divsf3.c`
  and `divdf3.c` were retired because they really are unreachable — `divsf3`/`divdf3`/
  `divhf3` expand straight to `fdivw`/`fdivd`/`fdivh`. The vector ones are different:
  there is no vector `fdiv`, so on lvx-2 a `v4sf` division still emits `call __divv4sf3`.
  Latent while libgcc does not build, but it needs the same lvx-2 multilib.

## KVX heritage: exact versus seed

`frec*` and `frsr*` in KVX were the **exact** reciprocal and reciprocal square root.
LVX generalises them with `fdiv*` and `fsqrt*`, which is why no `frec*` exists here.
They are **not** the same as `fsrec*`/`fsrsr*`, which are *seeds* — approximations meant
to be refined. Mapping one onto the other silently degrades precision, and nothing
catches it: it builds, the mnemonic exists, the mddump audit passes, the assembler is
happy, and the differential harness has no floating point. A seed belongs only behind
`flag_reciprocal_math`, `flag_unsafe_math_optimizations`, the `rsqrt` optab, or an
explicit `__builtin_lvx_fsrec*` call.
